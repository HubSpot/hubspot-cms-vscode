# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Dependencies

This project commits **both** `yarn.lock` and `package-lock.json`. When adding or updating any dependency, run both:
```bash
yarn install   # updates yarn.lock
npm install    # updates package-lock.json
```
CI uses `npm install`, so both lockfiles must stay in sync. `package-lock.json` is also published with the extension itself (it is not in `.vscodeignore`).

## Architecture

### Entry Point & Activation

`src/extension.ts` exports `activate()`, which wires together all subsystems in order:
1. Library logging + env setup
2. Tracking initialization
3. Command, URI handler, provider, and panel registration
4. Event registration
5. Config initialization (after events, so `ON_CONFIG_FOUND` fires correctly)
6. Post-registration: feedback prompt, terminal, status bar, HubL auto-detect, project config validation

### Source Layout

| Directory | Purpose |
|---|---|
| `src/commands/` | VS Code command handler registrations; `index.ts` aggregates all via `registerCommands()` |
| `src/providers/` | VS Code providers (completions, tree views, text document content); `index.ts` aggregates via `registerProviders()` |
| `src/features/` | Self-contained feature modules (linting, status bar, project validation, feedback) |
| `src/events/` | Internal VS Code event handlers (not contributed to `package.json`); `index.ts` aggregates via `registerEvents()` |
| `src/panels/` | Webview panel implementations |
| `src/lib/` | Shared utilities with no VS Code UI dependencies; unit-tested |
| `src/__mocks__/vscode.ts` | Manual VS Code API mock — enables vitest to run outside a real VS Code process |

### Registration Pattern

Every subsystem (commands, providers, events, panels) follows the same pattern: each module exports a `register*()` function, and the `index.ts` in that directory aggregates them. Adding a new command, provider, or event means: create the module, export a `register*()` function, and import it in the appropriate `index.ts`.

### Constants

All command IDs, event names, provider IDs, and tracked event names live in `src/lib/constants.ts` as typed objects (`COMMANDS`, `EVENTS`, `PROVIDERS`, `TRACKED_EVENTS`, `EXTENSION_CONFIG_KEYS`). Always use these constants rather than raw strings.

### UI Gating

The `hubspot.configPath` VS Code context key gates most menus, views, and UI contributions. It is set when a `hubspot.config.yml` is found in the workspace. Features that should only appear when HubSpot is configured must check this key.

### Build System

Webpack (`webpack.config.js`) produces two bundles in `dist/`:
- `extension.js` — the main extension bundle (target: `node`, external: `vscode`)
- `processFieldsJs.js` — a fork of `@hubspot/local-dev-lib`'s fields processor, spawned as a child process at runtime

Two custom webpack loaders (`scripts/loaders/`) patch `import.meta.url` and dynamic `import()` in dependencies for Node.js compatibility.

### Snippets

`snippets/auto_gen/` is fully generated by `yarn generate` — never edit these files manually. `snippets/man_gen/` is hand-maintained.

### Testing Notes

Unit tests live in `src/lib/__tests__/` and use vitest. The `vscode` module is aliased to `src/__mocks__/vscode.ts` in `vitest.config.ts` so tests run in a plain Node environment.

Acceptance tests (`acceptance-test/`) run in a real VS Code Electron instance via `@vscode/test-cli`. In CI they run under `xvfb-run -a`. The `.vscode-test.mjs` config sets `--user-data-dir /tmp/vsc-ext-test` to avoid Unix socket path-length issues in deep worktrees.
